# Условия срабатывания: события и наблюдения

Третий слой спецификации поверх [обзора взаимодействия](interaction-overview.md): когда ядро мира создаёт события и что каждая сущность видит в кадре. Формулы, на которые ссылаются условия, — в [расчётах](calculations.md); правила шага и протокол — в [концепции](../language-runtime-design.md).

## 1. Определения

| Термин | Кто создаёт | Что это |
|---|---|---|
| Намерение | ВМ | Запрос «хочу изменить мир»; проверяет и применяет ядро |
| Событие ядра | World Kernel | Зафиксированный факт перехода `S_k → S_(k+1)`; доставляется в кадре `k+1` или позже |
| Наблюдение | Координатор (по данным ядра) | Поля кадра — проекция снимка `S_k` на окружение сущности |
| Личное сообщение | ВМ (`send`) | Данные между программами; ядро не проверяет содержание, маршрутизирует координатор |

## 2. Общие правила

| Правило | Формулировка |
|---|---|
| Попытка ≠ успех | Намерение подтверждается событием ядра (дискретные действия) или наблюдением результата (распределительные запросы); сам факт отправки команды ничего не гарантирует |
| Доставка ≥ 1 тик | Любое событие и сообщение попадает в следующий кадр; нулевые задержки запрещены |
| Причинность | Событие несёт `event_id`, `causation_id`, `tick`, `entity_id`; от проводки прослеживается исходная поломка |
| Идемпотентность | Дубликат `(run_id, entity_id, tick, sequence)` не применяется второй раз |
| Пустой кадр | «Новых событий нет» — тоже валидный кадр; `every`-таймеры приходят в нём же |
| Всё по снимку | Условия всех событий шага вычисляются по `S_k` и результатам фаз этого же перехода, не по времени прихода пакетов |

## 3. Каталог событий ядра

| Событие | Условие возникновения | Получатели |
|---|---|---|
| `ActionSucceeded` | Дискретное намерение (урон, ремонт) прошло проверку фазы 1 и применено | Исполнитель |
| `ActionRejected(причина)` | Дискретное намерение отклонено: дистанция, исполнитель мёртв/сломан, нет ресурса | Исполнитель |
| `DamageApplied(цель, сумма, причина)` | Фаза урона: ≥ 1 допустимая атака по объекту (§7.1 расчётов) | Исполнитель, владелец объекта |
| `ObjectBroken(объект, причина)` | Переход `H > 0 → H = 0`. Причина: атака, вандализм, погода (§7.3), замерзание (§6.2) | Владелец, все бригады (создаётся задание), журналы |
| `EntityDied(сущность)` | `H = 0` у жителя или ксеноморфа (§7.2: атаки или урон от холода) | Журналы; ВМ сущности остаётся в барьере |
| `PowerLost` | Потеряна связность с работающим источником: поломка участка или источника; ИБП разрядился после потери сети | Дом, приборы дома |
| `PowerRestored` | Связность с работающим источником восстановлена | Дом, приборы дома |
| `WaterLost` | Потеря связности с источником по исправным трубам (§6.1) | Дом |
| `WaterRestored` | Связность восстановлена | Дом |
| `RepairCompleted(объект)` | `done ≥ T_rep` (§9) | Бригада, владелец объекта |
| `RepairRejected(причина)` | Нет денег, материалов или доступа при заявке/исполнении | Бригада, владелец |
| `ArrivalConfirmed(точка)` | `|target − pos| ≤ ε` (§8) | Агент |
| `MonthClosed(месяц)` | Граница 30 модельных суток | Отчёты и дашборд; ВМ не получают |

`PowerLost` и поломка участка — один и тот же шаг: урон фазы 2 меняет связность фазы 3 (§2 расчётов). `ObjectBroken(труба, замерзание)` обнаруживается в фазе 4, поэтому `WaterLost` приходит на шаг позже.

Два разграничения. Во-первых, дефицитный срез мощности не создаёт `PowerLost`: связность сохраняется, фактическая мощность видна в наблюдении `power_granted` (§5). Во-вторых, подтверждения `ActionSucceeded`/`ActionRejected` касаются только дискретных намерений — урона и ремонта; распределительные `power.request` и `motion.request` событиями не подтверждаются, их результат виден в наблюдениях `power_granted` и `position` следующего кадра (§5 обзора). Иначе ~600 приборов с правилами `every 1s` генерировали бы десятки миллионов подтверждений в сутки при квотированных очередях брокера. Превышение квоты — диагностируемая ошибка прогона, а не предметный отказ (концепция §6).

## 4. Таймеры и отложенная доставка

- `every P` срабатывает при `t mod P = 0`; отметка о сроке включается в кадр, порядок обработчиков — концепция §5.2.
- `hazard` разрешён только в обработчике периода `Δt`; в редких правилах — явно периодический `chance` (концепция §7.5).
- Отложенная доставка события задаётся `delivery_tick ≥ k+1`; обработка «по факту прихода из сети» запрещена.

## 5. Наблюдения: общие правила

- Кадр содержит только окружение сущности, не копию мира; пустой список наблюдений допустим.
- Списки ограничены радиусом `R_obs` и размером `N_obs`; сортировка `(distance, entity_id)`; `nearest` наследует этот порядок.
- Моделируемая связь отличается от транспорта брокера (правило 12 обзора): повреждённый канал связи делает удалённые датчики `Unknown` (`Option`), локальные датчики работают; TCP-соединение ВМ живёт.
- Производные поля вычисляет ядро при формировании кадра:

| Поле | Определение |
|---|---|
| `power_connected` | Объект на участке, связном с работающим источником (запрошенная мощность может быть нулевой — это не отключение) |
| `broken` | `H = 0` (§7.1) |
| `cold` | `T_inside < T_cold` — порог манифеста, порядок `10°C` |
| `water_available` | Связность с источником по исправным трубам (§6.1) |

## 6. Схемы наблюдений по видам сущностей

Схема `view` зависит от вида сущности (концепция §7.1). Ниже — состав MVP; расширение набора — новая версия схемы кадра.

### Дом

| Поле | Что это |
|---|---|
| `occupants` | Число живых жителей в зоне дома (§8 расчётов) |
| `temperature` | `T_inside` дома (§5) |
| `power_connected`, `water_available` | Связность сетей |
| `devices` | Список своих приборов: `id`, вид, `broken` |

### Прибор (обогреватель, чайник)

| Поле | Что это |
|---|---|
| `home_occupants` | Присутствие людей в доме-владельце |
| `power_connected`, `broken` | Локальные условия (пример §7.2 концепции) |
| `power_granted` | Фактически выделенная мощность прошлого шага (§4.3 расчётов) |
| `water_temperature` | Для чайника: температура воды (§5) |

### Житель

| Поле | Что это |
|---|---|
| `position` | Координата (§8) |
| `health` | Собственное здоровье; убывает от холода (§7.2) и атак |
| `cold` | Производное от `T_inside` дома, где находится |
| `reachable_breakables` | Испправные приборы в радиусе `R_vandal` своей зоны: `id`, `distance` |
| `time` | Модельное время кадра |

### Ксеноморф

| Поле | Что это |
|---|---|
| `position` | Координата |
| `visible_infrastructure` | Узлы в радиусе `R_sight`: `id`, вид, `position`, `distance`, `H` |
| `visible_humans` | То же для жителей; используется программами охоты (расширение MVP) |
| `patrol_waypoint` | Точка патруля из манифеста; обновляется по `ArrivalConfirmed` |

### Вездеход с бригадой

| Поле | Что это |
|---|---|
| `position`, `speed_eff` | Координата и эффективная скорость (§8) |
| `active_jobs` | Активные задания посёлка: объект, тип поломки, координата, `done/T_rep` |
| `materials_remaining` | Запас материалов на борту (РП) |

### Узлы инфраструктуры (реактор, солнечная станция, ИБП, насос, узлы связи)

| Поле | Что это |
|---|---|
| `mode` | Текущий режим узла (выбирает его программа) |
| `output_power` | Фактическая отдача прошлого шага (§4) |
| `charge` | Для ИБП: `E_ups/E_ups_max` |
| `flow` | Для насоса: фактическая подача |
| `links_up` | Для узла связи: состояние смежных каналов |

## 7. Личные сообщения между ВМ

Доставляются координатором по схеме события отправителя (`source_entity_id`, `source_sequence`); содержание ядро не проверяет. Состав MVP:

| Сообщение | Направление | Условие появления у получателя |
|---|---|---|
| `HeatingDemand { enabled }` | Дом → обогреватель | Отправлено программой дома (§7.2 концепции) |
| `Boil` | Житель → чайник | Команда жильца |
| `TeaReady` | Чайник → житель | Программа чайника увидела `water_temperature ≥ T_boil` |

## 8. Пример: каскад в событиях и наблюдениях

Значения из примеров [расчётов](calculations.md) (τ ≈ 13.9 ч, `K_freeze = 5400 K·s`):

| Шаг | Что происходит | Что видят сущности |
|---|---|---|
| k | Ксеноморф отправил `damage.request`; ядро: урон допустим, `H столба → 0`, `ObjectBroken(столб, атака)` | Бригады получают задание; `DamageApplied` — исполнителю |
| k | Связность сети пересчитана в фазе 3: участок мёртв | `PowerLost` домам за столбом — в кадре `k+1` |
| k+1 | Обогреватели видят `power_connected = false`, запрашивают `0W`; ядро выделяет ноль | Дом начинает остывать по §5 (без события — температура видна в кадре) |
| k+m (~5.6 ч) | `T_inside` перешла через `0°C`; трубы копят `exposure`, у жителей убывает здоровье (§7.2) | Жители видят `cold` и `health`; стресс растёт в их программах |
| k+n | `exposure ≥ K_freeze` для трубы: `ObjectBroken(труба, замерзание)` | Бригаде — второе задание; `WaterLost` дому — со следующего шага |
| k+s | Бригада прибыла (`ArrivalConfirmed`), ремонт идёт: `done` растёт | Прогресс виден в `active_jobs` всех бригад |
| k+e | `done ≥ T_rep`: `RepairCompleted`, `H → H_max`, `exposure → 0` | Проводка материалов и работ (§10.3); связность сетей восстанавливается |

Цепочка `event_id → causation_id` связывает атаку, обе поломки, ремонты и проводки — это же показывается на дашборде.

## 9. Открытые вопросы

- Рассылка `ObjectBroken` всем бригадам или назначение одной очередью заданий.
- Состав `visible_humans` и приоритеты охоты ксеноморфа — программа или наблюдения.
- Значения `R_obs`, `N_obs`, `R_sight`, `R_vandal` — после нагрузочного эксперимента (этап 1 плана).
- Событие «начался дефицит мощности» для дашборда: событие ядра или метрика наблюдения.
- Подтверждение доставки личных сообщений при ненадёжной моделируемой связи (концепция §7.2 — расширение после MVP).
