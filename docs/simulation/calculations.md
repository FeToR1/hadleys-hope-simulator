# Расчёты моделей ядра

Второй слой спецификации поверх [обзора взаимодействия](interaction-overview.md): формулы, которые исполняет World Kernel. Консолидирует модели из [концепции](../language-runtime-design.md) и доопределяет недостающие как рабочие предложения — они помечены **РП** и не считаются согласованными требованиями. Числовые значения — параметры манифеста. Поведенческие решения (кого атаковать, когда чинить) здесь отсутствуют: это программы Colony. Когда возникают события и что видно сущностям — в [условиях срабатывания](trigger-conditions.md).

## 1. Общие соглашения

- Шаг `Δt = 1s` модельного времени; `t = k × Δt`; все формулы применяются на переходе `S_k → S_(k+1)` по снимку начала шага.
- Единицы СИ; мощности в `kW/W`, температуры в `°C` (разности — в `K`), здоровье в `hp`, деньги — целые минимальные денежные единицы.
- Численный профиль версионируется: `Real64` для физических величин, фиксированный порядок суммирования (сортировка по `entity_id`), без NaN. Изменение формул или порядка меняет результат прогона.
- Каждый параметр манифеста имеет допустимый диапазон; выход за диапазон — ошибка связывания сценария до запуска, а не «авария колонии».
- Климат один на посёлок, дом — одно тепловое состояние, вода без гидродинамики: упрощения зафиксированы в концепции §11.

## 2. Порядок применения внутри шага

Фазы `WorldStep` фиксированы (концепция §5.3); формулы этого документа привязаны к фазам:

| Фаза | Что вычисляется | Раздел |
|---|---|---|
| 1. Проверка намерений | допустимость по `S_k`: жив ли исполнитель, дистанция, ресурсы | — |
| 2. Урон и ремонты | здоровье, поломки, завершение ремонтов | §7, §9 |
| 3. Сети и ресурсы | связность электросети и воды, распределение мощности и подачи | §4, §6 |
| 4. Интегрирование | тепло, замерзание труб, потребление, деньги | §5, §6, §10 |
| 5. Движение и присутствие | позиции, occupants | §8 |
| 6. События | формирование и адресация | [отдельный слой](trigger-conditions.md) |

Два исключения из «результат виден со следующего шага»: урон фазы 2 меняет связность сетей **уже в этом шаге** (повреждённый столб отключает дома на том же переходе); замерзание, обнаруженное в фазе 4, меняет доступность воды **только со следующего шага**.

## 3. Климат

Одна погода на весь посёлок. Профили задаются манифестом как функции модельного времени: `T_out(t)`, ветер `v_wind(t)`, осадки `p(t) ∈ {нет, дождь, снег}`, влажность, давление, интервал дня `[t_sunrise, t_sunset]`. Атмосфера не рассчитывается — климат является входом для электричества (§4), тепла (§5) и отказов (§7.3). Влияние влажности и давления в MVP — только на отчёты и наблюдения, не на формулы ниже.

## 4. Электричество

### 4.1 Доступная мощность

```text
P_reactor — отдаваемая мощность реактора; режим выбирает его программа (DSL),
            допустимые пределы — манифест
P_solar(t) = P_peak × f_day(t) × f_weather
f_day(t)   = 0 при t вне [t_sunrise, t_sunset];
            иначе sin(π × (t − t_sunrise) / (t_sunset − t_sunrise))          (РП)
f_weather  = 1.0 ясно, 0.5 облачно, 0.3 осадки — таблица манифеста           (РП)
P_ups_out  = min(P_ups_max, E_ups × η_out / Δt) — ИБП не отдаёт больше запаса
P_avail    = P_reactor + P_solar + P_ups_out
```

### 4.2 ИБП

```text
заряд:  E_ups' = E_ups + P_charge × Δt × η_in,
        P_charge = min(P_charge_max, max(0, P_gen − P_load))
разряд: E_ups' = E_ups − P_out × Δt / η_out, где P_out — дефицит, покрытый ИБП
E_ups ∈ [0, E_ups_max]; деградация ёмкости не моделируется (упрощение)
```

### 4.3 Распределение мощности

Потребители сортируются по `(priority_class, entity_id)`; классы — таблица манифеста. Рабочий пример приоритетов:

| Класс | Потребители |
|---|---|
| 0 | насос воды, узлы связи, заряд ИБП |
| 1 | обогреватели |
| 2 | чайники и прочая техника |
| 3 | уличное освещение |

```text
классы удовлетворяются целиком по порядку, пока хватает мощности;
граничный класс срезается пропорционально запросам:
P_granted_i = P_req_i × P_rest / Σ P_req_class                          (РП)
P_granted_i ≤ P_req_i всегда
запрос сломанного или обесточенного прибора отклоняется до распределения
```

Фиксированный порядок `(priority_class, entity_id)`, а не время прихода пакета — требование воспроизводимости из концепции §5.3.

## 5. Тепло дома

Сосредоточенная теплоёмкость, одна температура на дом (концепция §11):

```text
G = Σ_i (λ_i × A_i / d_i)        [W/K] — стены, окна, двери; каждое — своё слагаемое
C                                [J/K] — эффективная теплоёмкость дома
Q = Q_heat + Q_other             [W]
Q_heat   = η_heat × Σ P_granted по обогревателям дома
Q_other  — внутренние источники (люди, техника); параметр манифеста, по умолчанию 0 (РП)

G > 0:  T' = T_eq + (T − T_eq) × exp(−G × Δt / C),   T_eq = T_out + Q / G
G = 0:  T' = T + Q × Δt / C
```

Точное решение линейной модели вместо явного Эйлера исключает численный взрыв при любом допустимом `Δt`; `η_heat` — КПД обогревателя, для резистивного близок к 1. Вентиляция и тяга не моделируются (упрощение).

Числовой пример (значения сценария, не дефолты): `C = 10 MJ/K`, `G = 200 W/K`, постоянная времени `τ = C/G ≈ 13.9 ч`. Потеря питания при `T = +20°C`, снаружи `−40°C`, `Q = 0`:

```text
T(t) = −40 + 60 × exp(−t/τ)   →   0°C достигается за τ × ln(1.5) ≈ 5.6 ч
```

После перехода `T` через ноль внутренние трубы начинают копить мороз — §6.2. Так выглядит физическая, а не вероятностная связь «отключение → остывание → замерзание».

## 6. Вода

### 6.1 Подача и потребление

```text
насос: P_granted ≥ P_pump_req ⇒ Q_supply = Q_rated, иначе 0            (РП: порог, не пропорция)
граф подачи: дом снабжается ⇔ связан с источником по исправным трубам
дефицит подачи внутри единственного класса потребителей — пропорциональный срез
V_consumed,h += q_granted,h × Δt        [м³] — по факту выделенного
резервуар: W' = W + (Q_in − Σ q_granted) × Δt,  W ∈ [0, W_max]
Q_in — приток от источника в резервуар, параметр манифеста
```

### 6.2 Замерзание труб

```text
T_env(трубы) = T_inside дома для внутридомовых, T_outside для наружных   (РП)
exposure' = max(0, exposure + (T_fr − T_env) × Δt)      [K·s],  T_fr = 0°C
повреждение ⇔ exposure ≥ K_freeze(тип прокладки) — два отдельных параметра манифеста:
  K_freeze(внутридомовая) — порядок 5×10³ K·s
  K_freeze(наружная)      — порядок 10⁶ K·s: изоляция и глубина прокладки
ремонт сбрасывает exposure в 0
```

Формула симметрична: мороз накапливает `exposure`, оттаивание убывает с той же скоростью (решение по итогам обсуждения; раньше предлагался вариант «не убывает до ремонта»). Оттепель или восстановление питания реально спасают трубу — повторная короткая заморозка не ломает отогретую трубу почти мгновенно.

Примеры: внутридомовая труба при `K_freeze = 5400 K·s` повреждается за 1.5 ч при `−1°C` в доме и за 18 мин при `−5°C`; наружная при `K_freeze = 2×10⁶ K·s` и `−40°C` снаружи держит ~13.9 ч. Пороги обязаны быть раздельными: с единым порогом 5×10³ K·s вся наружная сеть ломалась бы за первые ~2 минуты холодного сценария. Модель копит градусо-секунды, а не бросает монету каждую секунду: требование концепции §11 для физического каскада.

## 7. Урон и исправность

### 7.1 Здоровье объектов

```text
H ∈ [0, H_max] (hp)
атака шага допустима ⇔ исполнитель жив в S_k, цель существует, дистанция ≤ R_attack(тип)
H' = max(0, H − Σ D_i)   — сумма допустимого урона, стабильный порядок по entity_id исполнителя
broken ⇔ H = 0
```

Одновременные атаки проверяются по одному снимку `S_k` и суммируются — правило 5 обзора. Объект с `H = 0` ремонтируется (§9); полное уничтожение (снос объекта из мира) — отдельный механизм вне MVP.

### 7.2 Здоровье жителей и ксеноморфов

Та же формула для атак. Дополнительно действует **урон от холода** (решение по итогам обсуждения; раньше предлагалось не моделировать):

```text
H' = max(0, H − k_harm × max(0, T_harm − T_inside) × Δt)
T_harm — порог вреда, порядок +5°C; k_harm — параметр, порядок 0.5 hp/(K·ч) (пересчитывается в hp/(K·s))
```

Пример: `T_harm = +5°C`, `k_harm = 0.5 hp/(K·ч)` — при `T_inside = 0°C` здоровье убывает на 2.5 hp/ч (житель гибнет за ~40 ч), при `−10°C` — на 7.5 hp/ч (~13 ч). Гибель (`H = 0`) от холода или атак — данные мира: прогон продолжается, ВМ сущности остаётся в барьере (правило 9 обзора). Стресс от холода остаётся отдельной величиной в программе жителя.

### 7.3 Погодные отказы

```text
λ_wire = λ0 + k_v × max(0, v_wind − v_th) + k_p × I_осадки    [1/s], на участок сети
I_осадки = 1 при осадках, иначе 0
p_отказа участка = 1 − exp(−λ_wire × Δt)
```

Испытание проводит ядро; точка случайного выбора регистрируется по схеме концепции §7.5 `(run_seed, entity_id, rule_name, site)`, расширенной на источники ядра: `entity_id` — служебный идентификатор `world`, `rule_name = weather_fault`, `site = segment_id` участка. Расширение схемы фиксируется в численном профиле версий (этап 4 плана). Случайность только инициирует поломку — дальнейшие последствия идут по детерминированным §4–§6.

## 8. Движение и присутствие

```text
v_eff = v_requested × s(поверхность)     — таблица манифеста: дорога 1.0, грунт 0.5 (РП)
|Δpos| = min(v_eff × Δt, |target − pos|); направление — по маршруту из графа дорог
arrival ⇔ |target − pos| ≤ ε; подтверждается событием ядра
столкновения и взаимное блокирование агентов не моделируются (упрощение)
occupants(дом) = число живых жителей с позицией в зоне дома; пересчитывается в фазе 5,
                 виден в кадре k+1 — источник задержки «один шаг» из концепции §5.4
```

Маршрут — кратчайший путь по графу дорог; пересчёт маршрута на каждом шаге не обязателен, повторный запрос движения меняет цель.

## 9. Ремонт

```text
норматив T_rep(тип поломки), материалы M(тип) — таблицы манифеста
прогресс: done' = done + Δt, пока бригада в зоне объекта; иначе стоит
завершение ⇔ done ≥ T_rep:  H → H_max, exposure → 0, broken снимается
стоимость — §10.3; недостаток денег или материалов — явный отказ с событием причины,
отрицательный склад не создаётся
```

Заявку создаёт событие поломки (см. [условия срабатывания](trigger-conditions.md)); выбор заказа — программа бригады.

## 10. Деньги

### 10.1 Накопление потребления

```text
E_h += P_granted,h × Δt  [Дж];   V_h += q_granted,h × Δt  [м³]   — на каждом шаге, по факту выделенного
```

### 10.2 Проводки за расчётный интервал

Интервал — модельный час; разбиение при смене тарифа или владельца (концепция §11.2):

```text
exact = Σ (потребление интервала × тариф)      — фиксированная точность
тарифы манифеста задаются за кВт·ч и м³; энергия переводится в кВт·ч
делением на 3.6×10⁶ при формировании проводки — коэффициент входит в численный профиль
r += exact; entry = floor(r); r −= entry        — перенос остатка округления между интервалами
```

Округление каждого секундного расхода исказило бы итог; перенос остатка сохраняет сумму.

### 10.3 Дискретные расходы

```text
ремонт: entry = c_parts(тип) + ставка × T_rep   — одной проводкой при завершении, на счёт владельца объекта
```

### 10.4 Календарь и отчёты

Модельный месяц — 30 суток (явное упрощение). Отчёты: общее имущество посёлка и каждый из владельцев; суммы отчётов сходятся с первичными проводками; внутренние начисления посёлка не учитываются в консолидированном расходе второй раз.

## 11. Открытые вопросы

- Деградация ИБП и учёт циклов заряда (вне MVP; приоритет заряда против обогрева подтверждён: заряд — класс 0).
- Разные множители проходимости для вездехода и жителя.
- Дневно-ночные тарифы: нужна ли смена тарифа по расписанию в MVP.

Решено по итогам обсуждения: симметричное убывание `exposure` при оттаивании (§6.2); урон от холода для здоровья жителей (§7.2); приоритет заряда ИБП — класс 0 (§4.3).
