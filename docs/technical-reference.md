# Технический справочник

Это описание существующего прототипа. Новую цель определяет [ТЗ](klyaksa-requirements.md), запуск — [README](../README.md).
Точные поля и правила следует смотреть в связанных исходниках; документация не дублирует весь код.

<a id="language"></a>

## Colony и сценарии

Язык задаёт поведение: `event`, `behavior ... for ...`, `param`, `state`, обработчики `on` и `every`;
внутри — `let`, присваивания, `if`, выражения и `send`. Типы и единицы проверяются семантически.

```colony
behavior HeaterControl for Heater {
    every 1s as regulate {
        if view.home_occupants > 0 && !view.broken && view.power_connected {
            power.request(2kW);
        } else {
            power.request(0W);
        }
    }
}
```

Синтаксис: [Colony.g4](../colony-dsl-parser/src/main/antlr/Colony.g4). Поддерживаемые виды, наблюдения,
события и возможности: [Contracts.kt](../colony-dsl-parser/src/main/kotlin/colony/semantics/Contracts.kt)
и генерируемый [contract.json](generated/contract.json). Новое имя вида в грамматике само по себе не добавляет его физику.
Контракт версии 7 добавляет `Human.medical_required` (необходимость посещения медцентра при включённом
креатине) и `Xenomorph.attack_active` (окно наземной атаки). Без соответствующей механики ядро возвращает
`false` и `true` соответственно; собственные кадры тестового стенда должны задавать читаемые программой поля.
Версия 8 добавляет отдельный вид `Predator` с наблюдениями и возможностями наземного хищника,
а также `Marine.visible_predators` для отдельного наблюдения этих угроз.
Сценарии Кляксы используют `GroundPredator` и тип снимка `predator`; `Xenomorph` остаётся в сценариях LV-426.

Каталог задаёт `sources` и шаблоны объектов; сценарий — каталог, `seed`, шаг, длительность и количества шаблонов.
Манифест разворачивает конкретные ID, параметры, родителей и координаты. Пути считаются от файла каталога/сценария.
`$instance` заменяется на `<prefix>-<номер>`; ID объекта — `<prefix>-<номер>/<роль>`.
С `world` наблюдения считает ядро; без него `view`/`changes` задают входы стенда. Совмещать эти источники нельзя.
Схема и лимиты: [Scenario.kt](../colony-dsl-parser/src/main/kotlin/colony/runtime/Scenario.kt).

## Исполнение

Текущие `run`/`serve` исполняют множество контекстов в одном JVM-процессе;
`HH_REFERENCE_WORKERS` задаёт число рабочих потоков поведения (по умолчанию 1). Во время исполнения
контекстов мир неизменяем; поля наблюдений вычисляются и кэшируются при первом чтении. Чтение представления
целиком материализует его до выхода из этой фазы. Результаты собираются в порядке манифеста до последовательной физики.
Программа проверяется один раз на fleet, отдельная ВМ по-прежнему проверяет переданный ей байт-код.
Периодические обработчики с неизменившимися зависимостями переиспользуют записи состояния и намерения,
сохраняя их порядок и бюджет инструкций. Чтение времени, случайность и отправка сообщений отключают этот кэш.
`run-native`/`serve-native` запускают брокер и общий пул C++ исполнителей. `HH_NATIVE_WORKERS` задаёт
1–32 процесса (по умолчанию 1); каждый обслуживает много независимых контекстов с общим байт-кодом.
Кадры и ответы передаются ограниченными пакетами по 512 контекстов; мир фиксирует только полный барьер тика.
Передача ядро JVM ↔ JVM-брокер и брокер ↔ C++ полностью двоичная, включая стартовый `broker.bin`.
Частный кодек `BrokerWire` сохраняет I64, порядок результатов и проверяет размеры сообщений;
[формат и ограничения](cvm-v2.md#9-частный-протокол-ядро-jvm--jvm-брокер).
`JsonElement` остаётся представлением некоторых значений в памяти; внешние HTTP/SSE и JSONL используют JSON.
`benchmark SCENARIO [TICKS]` измеряет эталонный прогон после 10 тиков прогрева: фазы шага,
полную сериализацию, размер снимка, GC и используемый heap. `benchmark-live` измеряет компактное кодирование.
`run-fast SCENARIO [OUTPUT.jsonl]` выполняет каждый тик, строя полный снимок только в конце. Его JSONL
содержит события и проводки всех тиков; промежуточные кадры имеют `full=false`, пустые `entities` и `effects`.
`benchmark-fast` измеряет эту политику снимков без записи журнала; финальное кодирование измеряется отдельно.
Запускать сравниваемые варианты последовательно; режимы benchmark вычисляют SHA-256 полного последнего снимка.

Тик: снимок мира → исполнение поведения → сбор намерений → проверка/разрешение конфликтов → физика → фиксация.
Личное состояние принадлежит контексту, физический мир — World Kernel. ВМ не меняет мир напрямую.
Все наблюдения тика читаются из одного снимка; события результата доставляются на следующем шаге.
Прибытие ответов по сети не определяет предметный порядок. Техническая ошибка останавливает прогон.

Инициализация читает параметры и ранее объявленное состояние, без наблюдений, случайности и эффектов.
События обрабатываются по `(sender, sequence)`, правила — в порядке объявления; таймеры включают тик 0.
Периоды положительны и кратны шагу; `hazard` требует периода, равного шагу. Ошибка ВМ откатывает её шаг.
Списки/записи живут в пределах шага; личное состояние хранит скалярные значения и их `Option`.

Эталонный JSON-артефакт v1: [Compilation.kt](../colony-dsl-parser/src/main/kotlin/colony/bytecode/Compilation.kt).
Семантика исполнения: [ReferenceVm.kt](../colony-dsl-parser/src/main/kotlin/colony/runtime/ReferenceVm.kt).
Двоичный артефакт и протокол: [CVM v2](cvm-v2.md).

## Мир, транспорт и деньги

Параметры и единицы: [WorldConfig.kt](../colony-dsl-parser/src/main/kotlin/colony/world/WorldConfig.kt).
Фазы, наблюдения, повреждения и расчёты: [WorldKernel.kt](../colony-dsl-parser/src/main/kotlin/colony/world/WorldKernel.kt).
Геометрия и сети: [Topology.kt](../colony-dsl-parser/src/main/kotlin/colony/world/Topology.kt).

Основные связи: исправность сети определяет доступность питания/воды; мощность распределяется по приоритетам;
тепловая модель дома интегрируется как `T' = T_eq + (T − T_eq) × exp(−G × dt / C)`, где `T_eq = T_out + Q/G`;
мороз накапливает воздействие на трубы, оттепель его уменьшает. Поломка запускает ремонт и расходы.
Начальный заряд UPS по умолчанию равен ёмкости; `upsInitialCharge` позволяет задать другой запас.
При дефиците реальных заявок UPS разряжается и не запрашивает заряд. В остальных случаях он заряжается
из внешней генерации как потребитель класса 0. Заряд и разряд исключают друг друга; потребители одного
граничного класса получают мощность пропорционально заявкам. Достижение нулевого запаса меняет связность
сети в следующей фазе распределения: UPS считается источником только при ненулевом запасе.
Труба, замёрзшая при интегрировании, отключает воду на следующем тике.

Ровер обеспечивает доступ к ремонту и перевозку; пассажир не движется независимо во время поездки.
Учитываются роли, вместимость, посадка/высадка и занятость транспорта. Распорядок жителей задан в программах Colony.

Деньги — целые минимальные единицы. Начисления используют фактическое потребление, перенос остатка округления и плательщика.
Доход `creatine_sale` учитывается отдельно от расходов. `MonthClosed` содержит расходы, доход и баланс
закрытого периода; его граница закрывает также незаписанные счётчики потребления. Новый период начинается
с нуля; накопительные суммы сохраняются отдельно. `monthlyReport()` возвращает открытый период,
`lastClosedMonthlyReport()` — последний закрытый.
Окно проводок ядра/UI ограничено; для полного журнала используйте JSONL, а не только текущий экран.

Новые механики отключены по умолчанию. [EcosystemConfig.kt](../colony-dsl-parser/src/main/kotlin/colony/world/EcosystemConfig.kt)
задаёт конечную зональную модель леса, навоза, планктона и состояния людей.
[EcosystemController.kt](../colony-dsl-parser/src/main/kotlin/colony/world/EcosystemController.kt) предлагает
служебные цели, факты и повреждения; ядро применяет их к общей физике. Уборщики едут к загрязнению,
набирают ограниченный груз и разгружаются на складе; движение и работа расходуют топливо.
Стационарный burner использует выделенную сетью мощность и общий конечный запас топлива.
Защита проверяет питание и боезапас; её расходы учитываются вместе с потреблением инфраструктуры.

`world.geometry` задаёт `coastX`, точки `mine`/`depository`/`medicalCenter`, список `gates`
и `gateWidth`. Ворота должны лежать на сгенерированном периметре; службы идут через ближайший
проём. Это маршруты с промежуточной точкой, без графа дорог. При включённой добыче шахта —
ремонтируемый объект `site/mine`; её поломка прекращает производство.
`defense.ammoRestockPerSecond` пополняет запас до `initialAmmoPerUnit` при наличии питания.
Уборка использует `initialDepotFuel`, `depotFuelCapacity`, `fuelRestockPerSecond` и физическую
дозаправку на депо до ёмкости бака `initialFuel`. Выжигание использует `fuelCapacity`,
`fuelRestockPerSecond`, `burnerCount` и `burnerSpacing`. Нулевые скорости означают отсутствие поставок.
Боеприпасы, топливо и ремонтные комплекты оцениваются при потреблении; пополнение не дублирует стоимость.
Электричество защиты и выжигания разделено на `defense_electricity` и `burn_electricity`.

## HTTP/SSE и UI

- `GET /health` — статус, прогон, тик, заданная скорость, ошибка, `houses`, `contexts`, `behaviorWorkers`,
  `nativeProcesses`, `observationMode` и `lastStepMs` (время шага без JSON); `GET /stream` — SSE снимков и статуса.
- `POST /control/pause`, `/resume`, `/step`, `/reset`; `/control/speed?value=N` задаёт шагов/с.
- Снимок: `version`, `runId`, `runtimeMode`, `seed`, `tickId`, `timestamp`, `full: true`, `entities`, `effects`, `events`, `postings`.
- Сущность: ID, реальный PID или `null`, тип, статус, метрики, координаты, связи и личное состояние.
- `causationId` связывает реальные события; состояния полные, события и проводки относятся к конкретному тику.

Точные схемы: [types.ts](../frontend/src/domain/types.ts); проверка входа: [dataSource.ts](../frontend/src/domain/dataSource.ts).
Экологические зоны отображаются площадными слоями леса, навоза и планктона, без значков в центре клетки.
На общем плане дома группируются; выбранный дом остаётся отдельным объектом, а клик по группе приближает карту.
Шлюз: [ObserverGateway.kt](../colony-dsl-parser/src/main/kotlin/colony/runtime/ObserverGateway.kt).
`timestamp` — модельное время. Новая `runId` сбрасывает UI; повторные тики игнорируются.
Переподключение использует `Last-Event-ID`; при вытесненной истории приходит `gap`.
Обычная история ограничена 256 снимками и 16 Mi символов JSON, клиентов — шестью.
При `HH_COMPACT_OBSERVER=1` хранятся до восьми структурированных снимков, дополнительно ограниченных
250 000 записями сущностей (минимум один снимок); полный JSON кодируется только по запросу обычного клиента.
`GET /stream?format=compact` отдаёт версию 2: полный первый кадр, затем изменения полей сущностей и `removed`.
`baseTick` должен совпадать с предыдущим тиком; после подключения, смены прогона или `gap` отправляется полная база.
Каждый тик передаёт все события и проводки; намерения `effects` остаются в полном `/stream` и JSONL.
UI проверяет конверт и изменённые сущности до фиксации кадра, переиспользуя ранее проверенные неизменённые
сущности; повторные тики не начисляют деньги повторно.
Карта использует пространственный индекс, отсечение за границами экрана, группировку домов/жителей/опор
при масштабе ниже 0,4 и общие графические контексты значков. Выбранная сущность остаётся отдельной.
Карта, топология, графики, расходы и инспектор показывают зафиксированное состояние; CSV содержит метрики снимка.
Sidebar также показывает фазовый портрет последних 10 000 точек и экспортирует их в CSV;
кнопка «Открыть 3D вихрь» отображает последние 3000 точек через Three.js.

## Проверки и случайность

Gradle проверяет язык, эталон, мир, интеграцию и нативную ВМ; CTest — нативный исполнитель;
Vitest — frontend. Наборы [conformance](../conformance) сравнивают Kotlin/C++/Python на одинаковых программах и кадрах.
Числа сравниваются по значению, порядок списков важен. Ошибочный шаг обязан сохранить прежнее состояние и счётчики.
`python conformance/run_vectors.py` проверяет векторы; команда CLI `conformance conformance` обновляет их.
CLI `contract docs/generated/contract.json` обновляет предметный контракт. Изменение семантики требует обновления проверок.

<a id="prng"></a>

Случайный поток: SHA-256 от seed, `entityId`, имени поведения, правила, точки вызова и счётчика;
53 старших бита первых восьми байтов делятся на `2^53`. Код: [random.cpp](../native/src/random.cpp);
точные входы и ожидаемые результаты: [prng.json](../conformance/prng.json).
`hazard(rate)` использует `1 − exp(−rate × dt)`. PID, поток и порядок обхода не входят в ключ случайности.
