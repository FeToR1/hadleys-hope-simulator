# Интеграция v1: DSL → конфигурация → стековая ВМ → UI

Статус: рабочий временный сквозной запуск в ветке `integration/dsl-frontend`.
Согласовано: JSON-конфигурация, временный исполнитель до появления ВМ участника команды,
предметные инструкции, сети Кана как ориентир. Аттрактор отложен.

## Что теперь запускается

```text
catalog.json ── sources ── .colony → ANTLR → AST → семантика → IR → program.cvm.json
      │                                                               │
scenario.json → populations/count → manifest.json → ReferenceRun → ReferenceVm × N
                                                        │                  │
                                                        └── события/намерения
                                                        │
                                              JSONL или HTTP/SSE → React
```

`ReferenceVm` исполняет стековые инструкции. Это отдельный экземпляр машины на каждый объект,
но **все временные ВМ находятся в одном JVM-процессе**. Требование преподавателя
«300+ отдельных процессов и отдельный брокер» эта итерация ещё не закрывает.
HTTP/SSE-сервис — шлюз наблюдения, а не брокер сообщений между процессами.

## Запуск

Нужен JDK 17; Gradle 8.8 загружается wrapper-ом. Команды ниже выполняются из корня репозитория:

```powershell
.\colony-dsl-parser\gradlew.bat -p colony-dsl-parser test installDist

# Проверка одного DSL-файла и компиляция в переносимый стековый артефакт
.\colony-dsl-parser\build\install\colony-dsl-parser\bin\colony-dsl-parser.bat check colony-dsl-parser/examples/heater.colony
.\colony-dsl-parser\build\install\colony-dsl-parser\bin\colony-dsl-parser.bat compile colony-dsl-parser/examples/heater.colony colony-dsl-parser/build/heater.cvm.json

# Компиляция всего пакета + развёртывание конфигурации без исполнения
.\colony-dsl-parser\build\install\colony-dsl-parser\bin\colony-dsl-parser.bat prepare examples/integration/colony-300.json colony-dsl-parser/build/demo

# Конечный прогон, один полный снимок на строку
.\colony-dsl-parser\build\install\colony-dsl-parser\bin\colony-dsl-parser.bat run examples/integration/small.json colony-dsl-parser/build/small.jsonl

# Наблюдение из UI; остановка Ctrl+C
.\colony-dsl-parser\build\install\colony-dsl-parser\bin\colony-dsl-parser.bat serve examples/integration/small.json
```

Во втором терминале:

```powershell
cd frontend
npm ci
npm test
npm run dev
```

Открыть адрес Vite и выбрать Live. Vite проксирует `/health` и `/stream` на
`http://127.0.0.1:8080`. Шлюз слушает только loopback. `serve SCENARIO PORT` меняет порт;
тогда нужно изменить и `frontend/vite.config.ts`.
Проверена сборка UI с Node 22.23.2. В Linux/macOS использовать `bash colony-dsl-parser/gradlew`
из корня и установленный скрипт CLI без `.bat`.

Шлюз начинает симуляцию при первом подключении `/stream`, делает один шаг каждые 300 мс
реального времени и останавливается после `ticks`. `step` — независимый шаг модельного времени.
`/health` сообщает `waiting`, `running`, `completed` или `failed`.
Для повторного запуска пока перезапустить `serve`; pause/reset API ещё нет.

## Разделение языка и конфигурации

1. **DSL** задаёт поведение, типизированные параметры, собственное состояние и реакции.
   В нём нет числа домов и имён конкретного запуска.
2. **Каталог** задаёт список исходников и шаблоны составных объектов. Например, `household`
   содержит `house`, `heater`, `kettle`, `resident`: у каждого своя программа и состояние ВМ.
3. **Сценарий** задаёт каталог, seed, шаг, длительность и количества шаблонов.
   `300 × household + 8 × alien = 1208` объектов/ВМ.
4. **Манифест** — результат развёртывания: конкретные ID, виды, программы, параметры,
   начальные наблюдения, родители и координаты. Он пригодится будущему supervisor-у.

Готовые примеры: [каталог](../examples/integration/catalog.json),
[малый запуск](../examples/integration/small.json),
[300 домов](../examples/integration/colony-300.json).
Пути каталога разрешаются относительно сценария, пути исходников — относительно каталога;
они не зависят от текущего рабочего каталога CLI.

ID имеет форму `<prefix>-<номер с 1>/<роль>`. `$instance` в строках шаблона заменяется
на `<prefix>-<номер>`. Например, параметр `"heater": "$instance/heater"`
станет `"heater": "home-42/heater"`. Префиксы должны быть уникальны.
Проверяются вид программы, набор и типы параметров, существование и вид `Ref<T>`,
поля наблюдений, ссылки родителей и цели запланированных изменений. Нулевой count допустим,
пустой запуск — нет. Лимит временного режима: 10000 объектов.

JSON-числа содержат канонические единицы: W, s, m, m/s, L, degC, hp;
`"2kW"` в JSON не принимается. В DSL единицы сохраняются: `2kW` компилируется в `2000` W.
Параметры enum пока не поддержаны в JSON: нужно добавить перечисление значений в ABI.
Внутренние enum/state DSL работают. `Option<T>`: `null` или `{"some": value}`.

`view` в каталоге — **временные входы стенда**, не альтернативное описание физики в DSL.
`changes` подменяет заданные наблюдения перед конкретным шагом, сохраняя остальные поля.
Это позволяет проверить уход людей, отключение питания и нагрев чайника до появления ядра.
В production наблюдения будет вычислять World Kernel.

## Правила исполнения

- Все файлы `sources` компилируются одним пакетом в указанном порядке. Имена событий и
  поведений общие, повторные объявления — ошибка. Event ID назначается по сортировке имён.
  Нельзя смешивать ID из разных артефактов. Диагностика пока указывает строку объединённого
  пакета; таблица исходных файлов/хешей — следующая доработка.
- Инициализаторы `state` исполняются один раз, по порядку объявления. Они могут читать
  параметры и уже объявленное состояние, но не view/time, случайность и внешние эффекты.
- Нумерация шагов начинается с 0. Таймер запускается при `tick % periodTicks == 0`,
  включая tick 0. Период должен быть положительным и кратным шагу симуляции.
- ВМ видят снимок наблюдений начала шага. Сначала обрабатываются входящие события
  по `(sender, sequence)`, обработчики одного события — в порядке объявления;
  затем таймеры в порядке объявления. Сообщения `send` доставляются на **следующем** шаге.
  Порядок внутри канала отправителя сохраняется; глобальная сортировка — правило стенда,
  а не требование классических сетей Кана.
- Параметры/view доступны только для чтения. Собственное состояние меняет только его ВМ.
  Предметные эффекты добавляют намерения в исходящий буфер; решение принимает язык,
  применение к миру выполняется после шага всех ВМ.
- `&&` и `||` используют короткое замыкание. Неисполненная случайная операция не расходует
  PRNG-счётчик. Состояние, счётчики и исходящая последовательность откатываются при ошибке
  одной ВМ; ошибка любой ВМ останавливает **весь запуск**. Возобновления после ошибки нет.
- Временные ограничители: 100000 инструкций/ВМ/шаг, 4096 элементов стека или списка целей,
  1024 исходящих сообщений и намерений/ВМ/шаг. Это не доказательство real-time дедлайна.

Случайность: отдельный счётчик для `(entityId, behavior, rule, site)`.
В SHA-256 подаются seed (signed i64 big-endian), затем четыре UTF-8 строки с длинами
(i32 big-endian), затем счётчик (i64 big-endian, начинается с 0).
Берутся старшие 53 бита первых 8 байт digest, результат делится на `2^53`.
`chance(p, site)` проверяет `u < p`; `hazard(rate, site)` использует
`p = -expm1(-rate * stepSeconds)`. `hazard` разрешён только в таймере с периодом Δt.
Одинаковый `site` в одном правиле разделяет счётчик; для независимых мест нужны разные строки.
Повторяемость проверена для reference-исполнителя; межъязыковую точность libm ещё нужно проверить.

## Стековый артефакт v1

`program.cvm.json` — текстовое переносимое представление стекового байт-кода, не бинарный формат
и не сериализация Kotlin-объектов. C/C++ ВМ должна читать этот контракт либо согласованный
эквивалент. Пока это v1 для интеграции; числовое кодирование инструкций не закреплено.

Корень: `version`, `stepSeconds` (decimal string), `events`, `behaviors`.
Поведение: `name`, `kind`, `params`, `state`, `temporaryCount`, `initialize`, `handlers`, `code`.
Обработчик содержит `entry` (индекс инструкции), `localCount` и ровно одно из
`eventId`/`periodTicks`. Инструкции имеют `op` и необязательные `arg`, `text`, `type`,
`names`, `value`, `line`, `column`; значения по умолчанию описаны в
[`Bytecode.kt`](../colony-dsl-parser/src/main/kotlin/colony/bytecode/Bytecode.kt).
Все слоты и адреса начинаются с 0. Стек пуст на входе и при `RETURN`.
Временные/локальные слоты заново создаются при входе в обработчик; state сохраняется.

| Группа | Инструкции / смысл |
|---|---|
| Значения и слоты | `CONST`, `LOAD/STORE_TEMP`, `LOAD_PARAM`, `LOAD/STORE_STATE`, `LOAD/STORE_LOCAL` |
| Входы | `LOAD_MESSAGE`, `LOAD_VIEW` (поле в text), `LOAD_OBSERVATIONS`, `LOAD_TIME`, `LOAD_SELF` |
| Выражения | `GET_FIELD`, `CONVERT`, `UNARY`, `BINARY`, `MAKE_RECORD`, `INDEX`, `CLAMP` |
| Option | `SOME`, `IS_SOME`, `UNWRAP` |
| Управление | `JUMP`, `JUMP_IF_FALSE`, `RETURN` |
| Предметные команды | таблица ниже |

Операнды кладутся на стек слева направо; справа — вершина. `BINARY` снимает right, затем left.
`MAKE_RECORD` снимает значения по списку `names` и создаёт JSON-объект.
`CONVERT` реализует разрешённые компилятором преобразования, в том числе Int64→Real64
и преобразование содержимого Option. Int64/Money — signed 64-bit с ошибкой переполнения;
вещественная арифметика — конечные IEEE-754 double. Деление на ноль — ошибка.

| Opcode | Входы → результат | Что объединяет |
|---|---|---|
| `NEAREST` | List&lt;Target&gt; → Option&lt;Target&gt; | обход списка, минимум distance, равенство по id; цели уже отфильтрованы ядром |
| `CHANCE` | probability, site → Bool | выбор потока, шаг PRNG, сравнение |
| `HAZARD` | rate, site → Bool | преобразование интенсивности с Δt + случайное решение |
| `POWER_REQUEST` | Power → ∅ | создание намерения потребления для собственной сущности |
| `MOTION_REQUEST` | Position, Speed → ∅ | создание намерения движения |
| `DAMAGE_REQUEST` | Ref/String, Health, reason → ∅ | создание намерения повреждения |
| `REPAIR_REQUEST` | Ref/String → ∅ | зарезервированный эффект; пока нет доступного вида с capability ремонта |
| `SEND` | адресат, значения полей → ∅ | формирование события, sender/sequence и помещение в исходящую очередь |

`Target = {id: String, position: {x: Distance, y: Distance}, distance: Distance}`.
Общие команды не заменяют правила поведения: в ABI нет `RUN_HOUSE_AI` или `RUN_XENOMORPH_AI`.
`BytecodeVerifier` проверяет версию, адреса, слоты, подписки, схемы SEND и высоты стека в CFG.
Полного доказательства типов/инициализации слотов для произвольного чужого байт-кода пока нет;
стенд предназначен для артефактов нашего компилятора.

## Что делает и чего ещё нет у ReferenceRun

Стенд применяет POWER_REQUEST как последнее запрошенное потребление, двигает объект по прямой
со скоростью × Δt и вычитает повреждение из исходных 100 hp. Списки целей задаёт сценарий;
их координаты/дистанции обновляются из текущих позиций. Погибшие цели убираются из списков.
Для обогревателя с parent количество людей берётся из наблюдений дома. Поломка становится
видимой на следующем шаге; защита самого обогревателя написана в DSL.

Это **упрощённые обработчики эффектов для проверки стыков**. Нет теплопередачи, электрического
баланса, воды, стоимости ремонта, навигации/столкновений, области видимости, работы/расписания
людей и полной модели смерти. Температура сама от мощности не меняется; её меняет сценарий.
`REPAIR_REQUEST` останавливает стенд с явной ошибкой. UI показывает только имеющиеся метрики.

## Контракт наблюдения v1

`GET /stream` отправляет стандартные SSE `data: <JSON>` с полными снимками:

```json
{
  "version": 1, "runId": "unique-run-id", "runtimeMode": "reference",
  "seed": "426", "tickId": 0, "timestamp": 1000, "full": true,
  "entities": [
    {"id": "home-1/house", "pid": null, "type": "house", "status": "nominal",
     "metrics": {"temperature": 16}, "connectedTo": [],
     "coordinates": {"x": 0, "y": 0}, "parentId": null, "vmState": {"demand": true}}
  ],
  "effects": [], "deliveredEvents": 0
}
```

`timestamp` — миллисекунды **модельного** времени после завершённого шага, не Unix epoch.
`pid=null` обязателен для reference; process-режим позже должен передавать реальный PID.
`seed` — строка, чтобы JS не терял точность 64-битного числа. `runId` новый при каждом запуске;
при сравнении повторных прогонов его исключают либо задают одинаковый в тестах.
`effects` — трасса намерений, ещё не полноценный граф причин/финансовый журнал.

Каждый snapshot независим: медленный наблюдатель может пропускать шаги, но не влияет на ВМ.
Шлюз держит только последний снимок, допускает до 6 одновременных SSE-клиентов.
Для полной трассы нужен `run ... OUTPUT.jsonl`. При переподключении передаётся текущий снимок.
Клиент проверяет формат, очищает мир при смене runId, игнорирует повторы/старые tickId,
удаляет отсутствующие сущности. При обрыве связи EventSource переподключается;
автоматической подмены данными mock нет. Примерная mock-цепочка причин скрыта в live.
CSV — экспорт доступных метрик снимка, а не финансовый отчёт.

## Следующие итерации и владельцы

1. **ВМ (#6) + codegen (#5):** согласовать v1 по этому документу, прочитать `program.cvm.json`,
   прогнать одинаковые программы через обе ВМ, проверить PRNG/числа/ошибки/лимиты.
2. **Брокер/supervisor (#2):** отдельный процесс брокера, отдельный OS-процесс каждой ВМ,
   загрузка manifest, барьер шага, READY/FRAME/RESULT, FIFO, дедлайны и отказ процесса.
   Транспорт и wire protocol ВМ ещё не реализованы; SSE их не заменяет.
3. **Симуляция (#7):** формировать типизированные view, валидировать и применять намерения
   к общему миру, реализовать физику/экономику, источник истинных метрик и причин событий.
4. **UI (#1):** подключаться к тому же observer v1 уже через production gateway,
   добавить управление запуском и реальные causal events вместо mock-сценария.
5. **Язык (#3/#4/#5):** source map для пакета, enum-схемы параметров, JSON Schema каталога,
   расширяемый контракт новых видов, дальнейшая верификация байт-кода и conformance-набор.

Старые дополнительные примеры Reactor/WaterNode/InternetNode демонстрируют желаемый синтаксис,
но не обещают семантическую поддержку этих видов. Рабочий набор текущего контракта:
House, Heater, Kettle, Human, Xenomorph. Количества/виды расширяются конфигурацией после
добавления соответствующих наблюдений и возможностей в контракт компилятора и ядра.

- Прогон 1208 временных ВМ на 30 шагов с JSONL-выходом.

- Chrome: mock → reference (9 объектов, seed 426) → топология → mock;
  без ошибок JavaScript и смешивания наборов объектов.
