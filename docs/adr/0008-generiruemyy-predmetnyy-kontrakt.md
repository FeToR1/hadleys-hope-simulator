# 0008. Генерируемый предметный контракт contract.json

- **Статус:** принято (реализовано в d3c42c1, 2026-09-21)
- **Дата:** 2026-09-21

## Контекст

Виды сущностей, их наблюдения (`view`), возможности, события ядра, intrinsics и единицы измерения нужны
одновременно: компилятору — для проверки программ, нативной ВМ — для схем, фронтенду и документации —
для отображения. Ручное дублирование этих сведений в коде и документах неизбежно расходится.

## Решение

- Единый источник — `ContractDocument` в коде компилятора (`colony/semantics/ContractDocument.kt`),
  из тех же определений, против которых компилятор проверяет программы.
- Команда CLI `contract docs/generated/contract.json` сериализует документ; файл закоммичен в репозиторий
  (`contractVersion`, `units`, `records`, `kinds`, `intrinsics`, `kernelEvents`) и сверяется тестом
  (`semantics/ContractDocumentTest`), который падает при устаревании.
- Документация ([spec/colony-language.md](../spec/colony-language.md), [glossary.md](../glossary.md))
  ссылается на contract.json и не дублирует его содержимое.

## Альтернативы

- Ручная спецификация в markdown — расползается от кода при каждом изменении.
- Генерация OpenAPI/JSON Schema — контракт описывает язык и мир, а не HTTP; формат не подходит.

## Последствия

- Изменение семантики языка/мира требует перегенерации контракта и обновления проверок — тест делает это обязательным.
- `contractVersion` в файле растёт при несовместимых изменениях; CVM-заголовок .cvm содержит версию контракта ([spec/cvm-format.md](../spec/cvm-format.md)).
- Открытый вопрос: машинно-читаемая схема самого HTTP/SSE (эндпоинты, кадры) пока не генерируется —
  см. [contribution/documentation-policy.md](../contribution/documentation-policy.md), раздел «Открытые вопросы».
